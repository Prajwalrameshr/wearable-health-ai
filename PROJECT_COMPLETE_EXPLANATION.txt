WEARABLE HEALTH AI - COMPLETE BEGINNER-FRIENDLY PROJECT EXPLANATION
====================================================================

Project name:
Wearable Health AI / Wearable Health Intelligence

Main idea:
This project analyzes wearable-device health data and converts raw daily readings into useful health intelligence. It takes signals such as heart rate, HRV, SpO2, steps, sleep, blood pressure, caffeine, screen time, workout type, mood, and environment data, then predicts the user's current physiological state, risk level, trend, and personalized recommendations.

In simple words:
The project tries to answer:

1. Is the user currently in a good recovery state, normal baseline state, or strain/stress state?
2. Is the user's body improving, stable, or deteriorating over time?
3. Which health risks are increasing?
4. What should the user do today?
5. How do weather and air quality affect the risk?
6. Which model performs better for this data?


1. WHY THIS PROJECT EXISTS
==========================

Wearable devices collect a lot of health data, but raw values are not always easy for a normal person to understand.

Example:
- Resting heart rate = 72 bpm
- HRV = 39 ms
- Sleep = 5.8 hours
- Steps = 3200

A beginner user may not know whether these values are good or bad. Also, the meaning depends on the person's own normal baseline. For one person, HRV of 45 may be normal. For another person, HRV of 45 may indicate poor recovery.

The ideology of this project is:

Use personal baseline comparison instead of judging everyone by one fixed rule.

This is important because wearable health is personalized. The same value can mean different things for different people. So the project creates rolling baselines for every user, measures deviations from those baselines, identifies health states using unsupervised machine learning, tracks temporal transitions using an HMM, and finally generates risk-aware recommendations.


2. HIGH-LEVEL PROJECT WORKFLOW
==============================

The complete workflow is:

Step 1: User uploads a CSV file or uses sample data.
Step 2: The app validates required columns.
Step 3: Data is cleaned and missing values are handled.
Step 4: Outliers are capped so extreme noisy readings do not dominate the model.
Step 5: Rolling personal baselines are created.
Step 6: Deviations from baseline are calculated.
Step 7: Temporal trend features are created using 7-day slopes.
Step 8: Severity and anomaly scores are calculated.
Step 9: Features are scaled for machine learning.
Step 10: KMeans or GMM groups daily records into health states.
Step 11: HMM studies how those states change over time.
Step 12: Risk scoring converts model output into readable risk levels.
Step 13: Environment data adjusts the risk score.
Step 14: Recommendation engine generates actions.
Step 15: Streamlit dashboard displays the final results.
Step 16: Processed results can be downloaded as CSV.

6. DATA PREPROCESSING IN DETAIL
===============================

Preprocessing happens mostly inside src/preprocessing.py.

6.1 Dataset resolution
----------------------

The function resolve_dataset_path() searches for known dataset filenames inside data/.

Known aliases:
- dwindables.csv
- wearables_hea;th_6mo_daily.csv
- wearables_health_6mo_daily.csv

Note:
The code contains a misspelled alias, but the correct dataset file exists as wearables_health_6mo_daily.csv.

6.2 Schema validation
---------------------

validate_required_columns() checks whether the uploaded file has enough columns to run the pipeline.

If the full schema is present, it passes.
If the minimal schema is present, it also passes.
If required columns are missing, Streamlit shows an error.

6.3 Filling optional fields
---------------------------

ensure_daily_schema() fills missing optional columns.

Examples:
- age default = 35
- gender default = unknown
- region default = unknown
- device_model default = generic
- height_cm default = 170.0
- weight_kg default = 70.0
- bmi default = 24.2
- sbp_mmHg default = 120.0
- dbp_mmHg default = 80.0
- sleep_efficiency default = 85.0
- caffeine_mg default = 0.0
- screen_time_min default = 0.0

This means a beginner can upload a simpler CSV and still run the project.

6.4 Date parsing and sorting
----------------------------

Dates are converted using pd.to_datetime().
Rows with invalid dates are removed.
Data is sorted by:
- user_id
- date

Duplicate records for the same user and date are removed, keeping the latest row.

6.5 Missing value handling
--------------------------

handle_missing() fills short gaps per user.

For numeric columns:
- forward fill
- interpolation
- backward fill

For categorical columns:
- fill using most common value per user
- if no mode exists, use "unknown"

This is useful because wearable devices sometimes miss data for a day.

6.6 Outlier handling
--------------------

remove_outliers() uses the IQR rule per user.

IQR means Interquartile Range:
IQR = Q3 - Q1

Values far below or above the normal range are capped.

Why:
Wearable devices can produce abnormal spikes due to sensor error. Capping prevents one bad reading from damaging the model.


7. FEATURE ENGINEERING IN DETAIL
================================

Feature engineering converts raw health readings into model-ready information.

7.1 Rolling personal baseline
-----------------------------

compute_baseline() calculates rolling 7-day averages per user.

Baselines created:

- baseline_hr from resting_hr_bpm
- baseline_hrv from hrv_rmssd_ms
- baseline_spo2 from spo2_avg_pct
- baseline_sleep from sleep_duration_hours
- baseline_steps from steps
- baseline_sbp from sbp_mmHg
- baseline_dbp from dbp_mmHg

Rolling standard deviations are also created:

- std_hr
- std_hrv
- std_spo2
- std_sleep
- std_steps
- std_sbp
- std_dbp

Why rolling baseline?
Because health is personal and changes over time. A rolling 7-day baseline compares today against the user's recent normal behavior.

7.2 Deviation features
----------------------

compute_deviation() calculates how far the current value is from baseline.

Examples:

hr_dev = resting_hr_bpm - baseline_hr
hrv_dev = hrv_rmssd_ms - baseline_hrv
sleep_dev = sleep_duration_hours - baseline_sleep
steps_dev = steps - baseline_steps

It also creates z-normalized versions:

hr_dev_z
hrv_dev_z
spo2_dev_z
sleep_dev_z
steps_dev_z
sbp_dev_z
dbp_dev_z

Why deviations?
Models should learn changes relative to the user, not only raw values.

Example:
If a user's normal resting heart rate is 58 and today is 72, that is meaningful strain.
If another user's normal resting heart rate is 72 and today is 72, that may be normal.

7.3 Temporal slope features
---------------------------

compute_temporal_features() creates 7-day trend slopes.

Features:

- hr_dev_slope_7d
- hrv_dev_slope_7d
- sleep_dev_slope_7d
- steps_dev_slope_7d
- hrv_cv_7d

Slope means direction over time.

Example:
If HRV is decreasing for several days, hrv_dev_slope_7d may become negative.
If sleep is improving, sleep_dev_slope_7d may become positive.

Why slopes?
One bad day is not always serious. A worsening pattern over many days is more important.

7.4 Severity score
------------------

compute_severity() calculates:

severity_score = sum of absolute z-deviation values

This combines multiple abnormal signals into one score.

If heart rate, HRV, sleep, SpO2, steps, and blood pressure all move away from baseline, severity_score increases.

7.5 Trend score
---------------

trend_score = sum of absolute slope values

This tells how strongly the user's health signals are changing.

7.6 Anomaly flag
----------------

anomaly_flag is set to 1 when severity_score is greater than:

user mean severity + 3 * user standard deviation

This marks unusually abnormal days.

7.7 Encoding categorical columns
--------------------------------

encode_features() one-hot encodes:

- workout_type
- mood

Example:
workout_type_run becomes 1 when workout type is run, otherwise 0.

This allows machine-learning models to use categorical information.

7.8 Scaling
-----------

scale_features() uses StandardScaler.

Scaling transforms values so they have comparable ranges.

Why scaling?
KMeans and GMM are distance/probability based. If one feature has huge numbers, such as steps, it can dominate smaller features like HRV deviation.


8. MODEL FEATURES USED
======================

The main clustering features are:

- hr_dev
- hrv_dev
- sleep_dev
- severity_score

These are used by both KMeans and GMM.

Why these features?

hr_dev:
Resting heart rate above baseline can indicate strain, illness, fatigue, or stress.

hrv_dev:
HRV below baseline can indicate lower recovery or autonomic stress.

sleep_dev:
Sleep below baseline can reduce recovery and increase fatigue risk.

severity_score:
Combines abnormal deviations into one health intensity value.

The project intentionally focuses on physiological state features rather than every column, because too many noisy features can confuse unsupervised models.


9. MACHINE LEARNING MODELS USED
===============================

The project uses three main model types:

1. KMeans
2. GMM
3. HMM

KMeans and GMM identify daily health states.
HMM studies how those states change over time.


10. KMEANS MODEL EXPLAINED
==========================

File:
src/kmeans.py

Model:
sklearn.cluster.KMeans

Purpose:
KMeans groups similar health days into clusters.

In this project, clusters are interpreted as:

- Recovery
- Baseline
- Strain

10.1 How KMeans works
---------------------

KMeans tries to divide data into K groups.

Each group has a center point called a centroid.
Each data point is assigned to the nearest centroid.

In this project:
Each row represents one user's one-day health state.
KMeans groups similar days together.

10.2 Why KMeans is used
-----------------------

KMeans is:

- Simple
- Fast
- Easy to explain
- Good as a baseline clustering model
- Useful when there are no manually labeled health states

Since the dataset does not appear to have true labels like "Recovery" or "Strain" manually assigned by doctors, unsupervised learning is appropriate.

10.3 KMeans implementation steps
--------------------------------

run_kmeans_pipeline() does:

1. Selects clustering features.
2. Removes invalid NaN/inf rows.
3. Computes elbow curve for K values 2 to 4.
4. Selects K = 3 if available.
5. Fits KMeans.
6. Assigns kmeans_cluster to each row.
7. Summarizes clusters.
8. Maps clusters to health labels.
9. Calculates metrics.
10. Optionally saves kmeans.pkl.

10.4 Cluster label mapping
--------------------------

The project uses a rule:

If HRV > 60, resting HR < 65, and sleep >= 7:
state = Recovery

If HRV < 40 and resting HR > 70:
state = Strain

Otherwise:
state = Baseline

This converts numerical clusters into human-readable health states.

10.5 KMeans metrics
-------------------

KMeans output includes:

- silhouette_score
- davies_bouldin_index
- calinski_harabasz_index
- risk_monotonicity

Silhouette score:
Higher is better. It means clusters are separated well.

Davies-Bouldin index:
Lower is better. It means clusters are compact and distinct.

Calinski-Harabasz index:
Higher is usually better. It measures cluster separation.

Risk monotonicity:
Checks whether severity increases in the expected order:
Recovery -> Baseline -> Strain

10.6 Limitations of KMeans
--------------------------

KMeans assumes clusters are round/spherical.
It gives hard labels only.
It may not represent uncertainty well.
It can struggle when health states overlap.


11. GMM MODEL EXPLAINED
=======================

File:
src/gmm.py

Model:
sklearn.mixture.GaussianMixture

Purpose:
GMM groups health days into probabilistic clusters.

11.1 How GMM works
------------------

GMM assumes the data is generated from multiple Gaussian distributions.

Instead of saying:
"This day is definitely cluster 1"

GMM can say:
"This day is 70% Baseline, 25% Strain, 5% Recovery"

This is useful for health because real physiology is not always clear-cut.

11.2 Why GMM is used
--------------------

GMM is used because:

- Health states overlap in real life.
- It provides probability/confidence.
- It can model softer boundaries than KMeans.
- It supports AIC and BIC for model selection.
- It is better suited when a day is between two states.

11.3 GMM implementation steps
-----------------------------

run_gmm_pipeline() does:

1. Selects GMM features.
2. Removes invalid rows.
3. Tests K values from 2 to 4.
4. Calculates AIC and BIC.
5. Selects K = 3 if available, otherwise chooses best BIC.
6. Fits GaussianMixture.
7. Predicts cluster labels.
8. Predicts cluster probabilities.
9. Maps clusters to Recovery, Baseline, Strain.
10. Adds probability columns:
   - prob_recovery
   - prob_baseline
   - prob_strain
11. Adds state_confidence.
12. Calculates metrics.
13. Optionally saves gmm.pkl.

11.4 AIC and BIC
----------------

AIC and BIC help compare GMM models with different numbers of clusters.

Lower AIC/BIC usually means a better balance between model fit and model complexity.

11.5 Why GMM may be ideal for this project
------------------------------------------

GMM is often better than KMeans here because health state is uncertain.

Example:
A user with slightly low sleep but normal HRV may be between Baseline and Strain.
GMM can express this uncertainty using probabilities.

11.6 Limitations of GMM
-----------------------

GMM assumes Gaussian-shaped distributions.
It can be sensitive to initialization.
It still needs good features.
It does not understand time order by itself.

That is why HMM is added after GMM/KMeans.


12. HMM MODEL EXPLAINED
=======================

File:
src/hmm_model.py

Model:
hmmlearn.hmm.GaussianHMM

Purpose:
HMM models the hidden temporal health state sequence.

12.1 Why HMM is needed
----------------------

KMeans and GMM look at each day mostly as a separate point.

But health is temporal.
Today's state depends on previous days.

Example:
If a user was in Strain for 5 days, tomorrow is more likely to remain Strain unless recovery improves.

HMM helps answer:

- How often does the user move from Recovery to Baseline?
- How often does Baseline become Strain?
- How long does a state persist?
- What is the hidden temporal state today?
- What is the future risk direction?

12.2 How HMM works in simple words
----------------------------------

HMM has:

Observed states:
The visible cluster labels from KMeans or GMM.

Hidden states:
The model's internal estimate of the real physiological condition.

Transition matrix:
A table showing probability of moving from one hidden state to another.

Example:
From Baseline:
- 70% chance stay Baseline
- 20% chance move Recovery
- 10% chance move Strain

12.3 HMM implementation steps
-----------------------------

run_hmm_pipeline() does:

1. Validates user_id, date, and observation column.
2. Sorts data by user and date.
3. Converts cluster labels into observation vectors.
4. Trains GaussianHMM with up to 3 components.
5. Decodes hidden state sequence.
6. Calculates posterior probabilities.
7. Maps hidden states to Recovery, Baseline, Strain based on severity.
8. Calculates state duration.
9. Calculates transition matrix.
10. Calculates transition rate.
11. Calculates state distribution.
12. Optionally saves an HMM model.

12.4 HMM outputs
----------------

The HMM output includes:

- decoded_df
- transition_matrix
- transition_rate
- state_distribution
- state_map
- duration_column
- probability_columns
- named_probability_columns
- model
- observations
- lengths
- observed_labels
- state_column

12.5 Transition rate
--------------------

Transition rate means how often the user's state changes.

High transition rate:
The user's state is unstable.

Low transition rate:
The user's state is stable.

12.6 State duration
-------------------

State duration tells how long the user remains in the same state.

This matters because one day of strain may be less serious than strain lasting a week.

15. HEALTH STATES USED
======================

The project standardizes states as:

Recovery
--------
The body appears well recovered.

Typical signs:
- Higher HRV
- Lower resting heart rate
- Good sleep

Baseline
--------
The body appears normal or average.

Typical signs:
- No major abnormal deviation
- Stable physiology

Strain
------
The body appears stressed or under recovery pressure.

Typical signs:
- Low HRV
- High resting heart rate
- Poor sleep
- Higher severity score


16. RISK SCORING SYSTEM
=======================

File:
src/risk_scoring.py

The risk scoring system converts model outputs and features into a 0 to 100 score.

Risk levels:

Low:
score below 40

Moderate:
score from 40 to 69.9

High:
score 70 or above

16.1 Health-risk categories
---------------------------

The project calculates multiple risk categories:

- Cardiovascular Strain
- Sleep Deficit Risk
- Chronic Stress Risk
- Recovery Failure Risk
- Overtraining Risk
- Fatigue Accumulation
- Burnout Risk
- Circadian Disruption
- Metabolic Stress
- Autonomic Imbalance

16.2 Inputs to risk scoring
---------------------------

Risk scoring uses:

- severity_score
- hrv_dev
- hr_dev
- sleep_dev
- sleep_duration_hours
- steps
- screen_time_min
- caffeine_mg
- environment values
- current state
- state confidence
- state duration
- early warning trend

16.3 State adjustment
---------------------

The risk score is adjusted based on current state:

Recovery:
Risk decreases.

Baseline:
Risk remains neutral.

Strain:
Risk increases.

16.4 Duration adjustment
------------------------

If the user remains in the same state for many days, risk can increase.

Why:
Persistent strain is more concerning than a one-day fluctuation.

16.5 Confidence adjustment
--------------------------

If the model is very confident about the state, the score can be adjusted upward.

16.6 Early warning adjustment
-----------------------------

If HRV and sleep slopes are both deteriorating, risk increases.


17. EARLY WARNING SYSTEM
========================

The early warning logic checks:

- hrv_dev_slope_7d
- sleep_dev_slope_7d

If both are negative enough, the project says the user is deteriorating.

Meaning:
HRV and sleep are moving in a bad direction together.

This is important because early warnings can detect problems before risk becomes extreme.


18. ENVIRONMENT-AWARE HEALTH INTELLIGENCE
=========================================

The project can use city-based environment data.

- temperature
- feels_like

- wind_speed

18.1 Environment impact rules
-----------------------------

If AQI is poor:
Risk increases and outdoor activity is discouraged.

If PM2.5 is high:
Respiratory risk increases.

If temperature is above 35 C:
Fatigue risk increases and hydration advice is given.

If humidity is high:
Sleep and recovery quality may be affected.

If weather is rain or thunderstorm:
Indoor activity is recommended.

18.2 Why environment matters
----------------------------

Wearable health does not exist in isolation.
Heat, pollution, humidity, and poor air quality can increase strain even if the user's internal signals look acceptable.

What is a .pkl file?
A .pkl file is a serialized Python object. It stores a trained model so it can be loaded later without retraining.

Why models are saved:

- Reuse trained models

- Avoid repeated training cost

25. WHY UNSUPERVISED LEARNING IS USED
=====================================

The project does not appear to have doctor-labeled target classes for every day.

Examples of labels that are missing:

- medically confirmed fatigue
- clinically confirmed stress
- diagnosed illness
- overtraining diagnosis
- recovery class assigned by expert

Because labels are missing, supervised learning is not the first choice.

Instead, the project uses unsupervised models:

- KMeans
- GMM

These models discover patterns in the data without needing labels.

Then rule-based mapping converts clusters into understandable health states.


26. WHY HMM IS USED AFTER CLUSTERING
====================================

Clustering creates daily states.
HMM models state sequence.

This is similar to:

Clustering:
"What is today's state?"

HMM:
"How did the user get here, how stable is this state, and where might the user go next?"

Health is not random day-by-day. Patterns matter.
That is why HMM adds value.

28. CURRENT LIMITATIONS
=======================

1. No true medical labels
-------------------------

The project uses unsupervised learning and heuristic mapping. This is useful for a final-year project, but it is not a clinically validated diagnosis system.

2. Health state mapping is rule-based
-------------------------------------

Clusters are mapped using HRV, resting HR, and sleep thresholds.
This is explainable but may not be accurate for every population.

3. Model persistence can be improved
------------------------------------

The project has .pkl files, but the main pipeline often retrains on the provided dataset. A production system should clearly separate:

- training
- validation
- model saving
- inference
- model versioning

4. Environment API is optional
------------------------------

If OPENWEATHER_API_KEY is not configured, default environment values are used.

5. Some older page files may be outdated
----------------------------------------

app/pages/analysis.py and app/pages/recommendations.py reference helper functions that are not present in the current dashboard_utils.py. The main app/main.py is the stronger current dashboard path.

6. No authentication
--------------------

The app does not currently have user login, role management, or secure account handling.

7. No database
--------------

Data is handled mostly through CSV upload and output files.

8. No clinical validation
-------------------------

The risk score is project logic, not a medically certified score.

9. Limited model evaluation
---------------------------

The project uses clustering metrics, but without real labels it cannot calculate accuracy, precision, recall, or F1 for true health outcomes.

35. BEGINNER-FRIENDLY GLOSSARY
==============================

CSV:
A spreadsheet-like text file used to store tabular data.

Feature:
A value used by a model, such as HRV deviation or sleep deviation.

Baseline:
The user's normal value calculated from recent history.

Deviation:
Difference between current value and baseline.

HRV:
Heart Rate Variability. Often used as a recovery and stress signal.

SpO2:
Blood oxygen saturation percentage.

Clustering:
Grouping similar data points without labels.

KMeans:
A clustering algorithm that groups points by nearest center.

GMM:
A probabilistic clustering model that gives state probabilities.

HMM:
A time-series model that estimates hidden states and transitions over time.

Transition matrix:
A table showing probability of moving from one state to another.

Silhouette score:
A clustering quality metric. Higher is usually better.

Davies-Bouldin index:
A clustering quality metric. Lower is usually better.

AIC/BIC:
Metrics used to compare GMM models. Lower is usually better.

Risk score:
A 0 to 100 number estimating health strain/risk.

Explainability:
Methods that show why a model made a prediction.

SHAP:
A popular model explanation method.


36. FINAL PROJECT SUMMARY
=========================

This project is a wearable health intelligence system.

It starts with raw wearable data and transforms it into:

- cleaned health records
- personalized baseline features
- deviation and trend signals
- health state classification
- temporal transition analysis
- risk scoring
- environment-aware adjustment
- personalized recommendations
- visual dashboard insights

The model ideology is:

1. Health should be personalized.
2. Today's reading should be compared with the user's own baseline.
3. Multiple signals together are more useful than one signal alone.
4. Time patterns matter.
5. Health states are uncertain, so probabilities are useful.
6. Recommendations should be understandable and actionable.

The project uses:

- KMeans as a simple baseline clustering model.
- GMM as a probabilistic health-state model.
- HMM as a temporal state-transition model.
- Rule-based and feature-based risk intelligence to make the output useful for users.

For a final-year project, this is a strong structure because it includes data preprocessing, machine learning, temporal modeling, risk scoring, recommendations, explainability, visualization, and future deployment potential.
