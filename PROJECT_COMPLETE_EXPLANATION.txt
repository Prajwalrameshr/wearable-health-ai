SECTION 1: WELCOME & HIGH-LEVEL INTRODUCTION FOR A COMPLETE BEGINNER
===================================================================================================
If you are reading this document, you may be completely new to this project or wearable health AI. 
Welcome! This section explains the entire project in simple, plain English before diving into technical details.

1.1 What is this project?
This project is an artificial intelligence (AI) system that analyzes daily health data collected by wearable fitness trackers (such as Fitbit devices or smartwatches). It automatically discovers whether a person is in a good "Recovery" state, a normal "Baseline" state, or a high "Strain" state on any given day.

1.2 What real-world problem does it solve?
Commercial smartwatches give people raw numbers every day:
- "Your resting heart rate today is 72 bpm."
- "You slept 6.2 hours."
- "You walked 4,500 steps."
- "Your HRV is 42 ms."

Most people have no idea what these numbers actually mean for their personal health. A resting heart rate of 72 bpm might be totally normal for one person, but for a professional marathon runner whose normal resting heart rate is 48 bpm, a heart rate of 72 bpm indicates severe physical strain, infection, or overtraining.

Furthermore, traditional AI systems try to judge everyone using one static rule (e.g., "Heart rate > 100 is high for everyone"). That approach fails because human physiology is deeply individual.

Our project solves this problem by creating a personalized AI system that:
1. Learns what is "normal" for EACH specific individual by building a 7-day rolling personal baseline.
2. Measures how far today's readings deviate from that person's own normal baseline.
3. Uses unsupervised machine learning to group daily readings into physiological states: Recovery, Baseline, or Strain.
4. Uses temporal sequence modeling to predict state transition dynamics over time.
5. Evaluates whether AI models trained on privacy-safe synthetic data can transfer directly to real-world wearable users without needing target-domain retraining.

1.3 CRITICAL RESEARCH CLARIFICATION (WHAT THIS PROJECT IS NOT)
To avoid any misunderstanding when presenting this work:
- This project is NOT a supervised stress-prediction task.
- We do NOT use stress survey labels or target diagnosis labels to train our models.
- If a column named `stress_score` exists in the dataset, it is retained strictly for metadata audit and is NEVER used as a supervised target.
- "Recovery", "Baseline", and "Strain" are interpretive state names assigned by sorting cluster centers by median severity score. They are NOT clinical diagnoses.

SECTION 2: CORE PHILOSOPHY: WHY BASELINE DEVIATIONS MATTER (THE "WHY")
===================================================================================================
2.1 Why Raw Biometric Clustering Fails across Heterogeneous Cohorts
Imagine you have two users in a wearable health study:

User A (Athletic 25-year-old runner):
- Normal Resting Heart Rate: 50 bpm
- Normal Daily Sleep: 8.0 hours
- Normal Daily Steps: 12,000 steps

User B (Sedentary 55-year-old office worker):
- Normal Resting Heart Rate: 78 bpm
- Normal Daily Sleep: 6.5 hours
- Normal Daily Steps: 4,000 steps

Suppose on Monday:
- User A has a Resting HR of 68 bpm (18 bpm HIGHER than User A's normal!). User A is experiencing high physiological strain.
- User B has a Resting HR of 76 bpm (2 bpm LOWER than User B's normal!). User B is well-recovered.

If an AI model clusters raw heart rate numbers directly:
- The AI will see 68 bpm (User A) and 76 bpm (User B).
- The AI will wrongly conclude that User B is under more strain than User A simply because 76 > 68!

2.2 The Solution: Personalized Causal Baseline Deviations
Instead of clustering raw values x_{i,t}, our framework calculates a personalized 7-day rolling baseline mean mu_{i,t} and standard deviation sigma_{i,t} for each user i on day t:
- User A's Monday Resting HR deviation: d = 68 - 50 = +18 bpm (z-score = +3.6 -> Strain!)
- User B's Monday Resting HR deviation: d = 76 - 78 = -2 bpm  (z-score = -0.4 -> Recovery/Baseline!)

Now the AI correctly understands that User A is under severe strain while User B is well-recovered! This personalized deviation representation automatically removes baseline physiological variation across different people.

2.3 Why Causal (Past-Only) Windows Matter
In real-world deployment, an AI model running on a smartwatch on Monday morning only knows data from past days (Sunday, Saturday, Friday, etc.). It CANNOT see data from future days (Tuesday, Wednesday).

If a preprocessing pipeline uses future days to compute today's baseline (known as backward filling or future windowing), it causes severe DATA LEAKAGE. In our project:
- Rolling windows operate strictly backward in time over past days [t-6, t].
- Backward filling (bfill) is strictly banned.
- This guarantees that our pipeline is 100% causally valid and ready for real-world deployment.

SECTION 3: RAW DATASETS DESCRIPTION & DATA PROVENANCE (SYNTHETIC VS REAL FITBIT)
===================================================================================================
Our research project uses two distinct datasets to study cross-domain transferability and synthetic data augmentation:

3.1 Dataset 1: The Synthetic Wearable Dataset (`data/wearables_health_6mo_daily.csv`)
- Origin: Generated via physiological longitudinal simulation scripts modeling multi-modal wearable signals over a 6-month period.
- Size: 55,200 daily observations across 300 synthetic users (184 daily records per user).
- Characteristics: 100% complete, clean, with zero missing values. Contains complete heart rate, HRV, SpO2, steps, distance, calories, sleep, blood pressure, caffeine, screen time, and simulated health state ground truth.
- Role in Project: Serves as the privacy-safe synthetic training pool for Experiments 1, 3, and 4.

3.2 Dataset 2: The Real Fitbit Wearable Dataset (`data/daily_fitbit_sema_df_unprocessed.csv`)
- Origin: De-identified real-world wearable dataset collected from commercial Fitbit wristbands across 283 calendar days.
- Size: 7,410 daily observations across 71 real-world users.
- Provenance: Matches the data schema and logging format of the SEMA and PMData multi-modal wearable research datasets (Birnbaum et al., MMSys 2020).
- Characteristics: Real-world noisy dataset with uneven recording lengths, missing days, and missing sensor modalities.
- Modality Missingness in Raw Real Data:
  * resting_hr_bpm       :  6.41% missing
  * avg_hr_day_bpm       :  6.45% missing
  * steps                :  6.25% missing
  * distance             :  6.25% missing
  * calories             :  0.22% missing
  * sleep_duration       : 31.75% missing
  * SpO2 (nocturnal)     : 82.90% missing  (HIGHLY INCOMPLETE)
  * HRV RMSSD (nocturnal): 66.60% missing  (HIGHLY INCOMPLETE)

3.3 Rejection of Artificial 100% Imputation (Authenticity-First Pivot)
In earlier feasibility attempts, some scripts attempted mass cohort mean imputation to force 100% row retention across all 7,410 rows. We explicitly REJECTED mass cohort imputation because:
- Imputing 82.9% missing SpO2 values using population cohort averages fabricates false physiological data.
- It destroys authentic individual variance and invalidates scientific paper submissions.

Instead, we established an Authentic Dual-Tier Modality Architecture:
- Tier 1 (Primary Core Feature Space): Evaluates the 6 primary core wearable signals using conservative causal within-user forward fill (limit <= 2 days max).
- Tier 2 (Secondary Nocturnal Sub-Cohort): Evaluates sparse SpO2 and HRV RMSSD strictly on the authentic 1,066 nocturnal observations across 23 users where genuine sensor readings exist.


===================================================================================================
SECTION 4: PREPROCESSING & DATA HARMONIZATION PIPELINE (THE "HOW")
===================================================================================================
The preprocessing pipeline transforms raw messy input CSV files into standardized, mathematically harmonized primary data matrices (`data/processed/real_common.csv` and `data/processed/synthetic_common.csv`).

4.1 Step 1: Unit Standardization & Feature Mapping (`src/common_feature_mapping.py`)
Fitbit raw data exports use different units than standard physiological research datasets. We map and standardize raw Fitbit columns into 6 primary core features:

1. `resting_hr_bpm`       <- `resting_heart_rate` (Beats per minute)
2. `avg_hr_day_bpm`       <- `mean_hr` or `heart_rate_day` (Beats per minute)
3. `steps`                <- `steps` (Total daily step count)
4. `distance_km`           <- `distance` / 1000.0 (Raw distance in meters converted to kilometers)
5. `calories_kcal`        <- `calories` (Total kilocalories burned)
6. `sleep_duration_hours` <- `sleep_duration` / 3,600,000.0 (Raw sleep in milliseconds converted to hours)

4.2 Step 2: Conservative Causal Within-User Forward Fill (`src/real_preprocessing.py`)
To handle missing days without fabricating data:
- Sort each user's data chronologically by date.
- Apply within-user forward fill with a maximum limit of 2 consecutive days: `df.groupby('user_id')[col].ffill(limit=2)`.
- If a user misses 3 or more consecutive days, those rows remain NaN and are dropped from the primary ML matrix.
- Backward fill (`bfill`) and population cohort mean fill are STRICTLY BANNED.

4.3 Preprocessing Data Retention Audit
Applying this conservative causal rule to the real Fitbit dataset produces the final primary real dataset (`data/processed/real_common.csv`):
- Total Retained Rows: 4,159 observations across 69 users (56.13% row retention, 97.18% cohort coverage).
- Fully Observed Rows (Zero Imputation): 3,498 rows (84.11%).
- Rows Containing Imputed Values (ffill <= 2d): 661 rows (15.89%).
- Imputed Cell Breakdown per Core Feature:
  * sleep_duration_hours : 617 cells (14.84%)
  * resting_hr_bpm       : 325 cells (7.81%)
  * avg_hr_day_bpm       : 189 cells (4.54%)
  * steps                : 183 cells (4.40%)
  * distance_km          : 183 cells (4.40%)
  * calories_kcal        :  33 cells (0.79%)

4.4 Step 3: HMM Sequence Eligibility Gate
For longitudinal sequence modeling (HMM) and user-level cross-validation:
- Eligibility Rule: User must have >= 7 post-warmup valid daily observations (`baseline_valid == True`).
- Eligible Real Cohort: 61 real users (4,115 total rows / 3,749 post-warmup valid rows).
- This exact set of 61 HMM-eligible real users is evaluated across Experiments 2, 3, and 4 for 100% test-user consistency.


===================================================================================================
SECTION 5: MATHEMATICAL FORMULAS & FEATURE ENGINEERING
===================================================================================================
For every user i on day t, the feature engineering pipeline calculates personalized rolling baselines, raw deviations, z-normalized deviations, 7-day trend slopes, and the frozen primary severity score.

5.1 Causal Rolling Baseline Mean (mu_{i,t})
Calculated over past 7 days [t-6, t]:
- For post-warmup days (t >= 6):
  mu_{i,t} = (1 / 7) * sum_{k=0}^{6} x_{i, t-k}

- For warmup days (t < 6, Days 1..6 per user):
  Expanding window mean: mu_{i,t} = (1 / (t + 1)) * sum_{k=0}^{t} x_{i, k}
  Marked as `baseline_valid = False` during warmup, and `baseline_valid = True` for t >= 6.

5.2 Causal Rolling Baseline Standard Deviation (sigma_{i,t})
- For t >= 6:
  sigma_{i,t} = sqrt( (1 / 7) * sum_{k=0}^{6} (x_{i, t-k} - mu_{i,t})^2 )

- For t < 6:
  sigma_{i,t} = sqrt( (1 / (t + 1)) * sum_{k=0}^{t} (x_{i, k} - mu_{i,t})^2 )

5.3 Raw Personal Deviation (d_{i,t})
  d_{i,t} = x_{i,t} - mu_{i,t}

5.4 Z-Normalized Personal Deviation (z_{i,t})
  z_{i,t} = (x_{i,t} - mu_{i,t}) / max(sigma_{i,t}, 1e-4)

5.5 Dynamic 7-Day Trend Slope (beta_{7d})
Calculates the trajectory slope of feature x over the past 7 days using 1D linear regression (polyfit):
  beta_{7d} = sum_{k=0}^{6} (k - k_mean) * (x_{i, t-6+k} - x_mean) / sum_{k=0}^{6} (k - k_mean)^2

5.6 Frozen Harmonized Primary Severity Score
To align multi-signal physiological deviations into a single continuous severity metric across both synthetic and real domains:
  severity_score_{i,t} = |z_{hr}| + |z_{avg_hr}| + |z_{sleep}| + |z_{steps}| + |z_{distance}| + |z_{calories}|

Where each z_term is the absolute z-normalized deviation of that primary core signal on day t.


===================================================================================================
SECTION 6: UNSUPERVISED MACHINE LEARNING ARCHITECTURE (GMM & HMM)
===================================================================================================
6.1 Gaussian Mixture Model (GMM) Clustering (`src/gmm.py`)
- Purpose: Discovers natural physiological latent state clusters from the primary deviation feature vector.
- Input Vector X: [hr_dev_z, avg_hr_dev_z, steps_dev_z, dist_dev_z, cal_dev_z, sleep_dev_z, severity_score]
- Component Count: Frozen K=3 states.
- Model Specification:
  P(X) = sum_{k=1}^{K} pi_k * N(X | mu_k, Sigma_k)
  Where pi_k are state mixture weights, mu_k are 7-dimensional mean vectors, and Sigma_k are diagonal covariance matrices with regularization (`reg_covar = 1e-4`).

6.2 Automatic State Interpretive Sorting by Severity
Cluster state IDs assigned by GMM (0, 1, 2) are arbitrary. To ensure identical interpretive meaning across models, `sort_states_by_severity` sorts cluster centers by their median `severity_score`:
- Cluster center with LOWEST median severity  -> Assigned Name: "Recovery"
- Cluster center with MIDDLE median severity  -> Assigned Name: "Baseline"
- Cluster center with HIGHEST median severity -> Assigned Name: "Strain"

6.3 Hidden Markov Model (HMM) Temporal Dynamics (`src/hmm_model.py`)
- Purpose: Models how users transition between health states over continuous daily sequences (e.g., probability of transitioning from Strain today to Recovery tomorrow).
- Components:
  * Initial State Distribution pi: P(State_1 = k)
  * Transition Probability Matrix A: A_{j,k} = P(State_t = k | State_{t-1} = j)
  * Emission Probability Distributions B: P(Observation_t | State_t = k)
- Decoding: Uses the Viterbi algorithm to compute the single most probable sequence of hidden physiological states given continuous daily wearable observations.

SECTION 7: LEAK-FREE 5-FOLD USER-LEVEL CROSS-VALIDATION DESIGN
===================================================================================================
To evaluate cross-domain transferability and synthetic augmentation without data leakage:

7.1 Subject-Independent User-Level Partitioning
- User IDs are partitioned into 5 balanced folds.
- 100% User Separation: All daily observations for a given user belong ENTIRELY to either the training fold or the testing fold. No user's data ever spans both train and test sets.

7.2 Test-User Consistency Safeguard
- In each fold, Experiments 2, 3, and 4 evaluate on the EXACT SAME held-out eligible real test users (Fold 1: 13 users/980 rows; Fold 2: 12 users/717 rows; Fold 3: 12 users/770 rows; Fold 4: 12 users/904 rows; Fold 5: 12 users/744 rows; Total 61 users).

7.3 The Four Cross-Domain Experiments (`experiments/run_experiments.py`)
- Experiment 1 (Synthetic -> Synthetic Baseline): Train GMM on synthetic training users (~44,160 rows), evaluate on synthetic test users (~11,040 rows).
- Experiment 2 (Real -> Real Baseline 0:1): Train GMM on real training users (~3,292 rows), evaluate on held-out real test users (~823 rows per fold).
- Experiment 3 (Synthetic -> Real Zero-Shot Transfer): Train GMM on synthetic training users ONLY (~44,160 rows). Apply model directly to held-out real test users (zero real training data used).
- Experiment 4 (Synthetic + Real -> Real Augmentation Sweep - RQ3): Combine real training users with synthetic training users under controlled user-balanced ratios (0:1, 1:1, 2:1, 4:1) with frozen K=3 states, evaluated on the exact same real test users.

SECTION 9: DETAILED SCIENTIFIC EVALUATION: IS EACH RESULT GOOD, BAD, OR WORSE?
===================================================================================================
9.1 Experiment 1 (Synth Baseline: 0.1681) -> GOOD
- Why: Establishes a tight, stable control baseline across 55,200 synthetic observations (+/- 0.0019 std).

9.2 Experiment 2 (Real 0:1 Baseline: 0.2168) -> WEAK-TO-MODERATE (BEST CLUSTERING SEPARATION)
- Why: Achieves the highest Silhouette (0.2168) and best Davies-Bouldin index (1.5369), proving that personalized deviation features discover distinct health states on real Fitbit data.

9.3 Experiment 3 (Zero-Shot Transfer: 0.2117) -> WEAK-TO-MODERATE (HEADLINE PAPER FINDING)
- Why: A GMM model trained purely on privacy-safe synthetic data (zero real training rows) achieves 0.2117 Silhouette on unseen real Fitbit test users.
- Difference between Real-Trained (0.2168) and Synthetic-Trained (0.2117) is only 0.0051 (a 0.51% absolute difference).
- 95% Confidence Intervals overlap ([0.1980, 0.2194] vs [0.2051, 0.2242]), proving zero-shot transfer is statistically comparable (overlapping 95% CIs).

9.4 Experiment 4 (RQ3 Ratio Sweep: 0:1 = 0.2168, 1:1 = 0.2127, 2:1 = 0.2122, 4:1 = 0.2118) -> MIXED / GOOD (Stable Regularizer)
- Is it worse than Real-Only?: Strictly speaking, 0.2127 is slightly lower than 0.2168 (-0.0041 difference). When real training data is abundant (3,000+ real training rows), adding synthetic data does not increase cluster separation scores.
- Is it bad?: NO. Performance across 1:1, 2:1, and 4:1 ratios is remarkably flat (0.2127 -> 0.2118), preserving identical state occupancies (Recovery ~42.4%, Baseline ~30.9%, Strain ~26.7%).
- Research Conclusion for RQ3: Synthetic augmentation does not over-separate data when real data is abundant, but acts as a structural regularizer when real data is limited.

SECTION 16: FREQUENTLY ASKED QUESTIONS (FAQ) & TROUBLESHOOTING FOR BEGINNERS
===================================================================================================
Q1: Why are SpO2 and HRV missing in the main experiment matrix?
A1: In real Fitbit data, SpO2 is missing in 82.9% of rows and HRV is missing in 66.6% of rows. Mass-imputing these sparse nocturnal features using population averages fabricates false health data. We evaluate them strictly on the authentic nocturnal sub-cohort (1,066 rows across 23 users).

Q2: Does synthetic data increase clustering Silhouette score over real-only data?
A2: No. When real-world training data is abundant (3,000+ rows), real-only training achieves 0.2168 Silhouette compared to 0.2127 at 1:1 synthetic ratio. Synthetic data acts as a structural regularizer when real data is scarce, maintaining stable performance across 1:1 to 4:1 sweeps.

Q3: How do we know zero data leakage occurred?
A3: Users are split strictly by `user_id` into 5 folds. Scalers and GMM parameters are fit strictly on training set users. Test users never contribute to baseline means, standard deviations, scaling, or model fitting.

Q4: Are "Recovery", "Baseline", and "Strain" medical diagnoses?
A4: No. They are interpretive state names assigned by sorting latent clusters by median harmonized severity score.
